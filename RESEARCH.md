Design choices: named profiles, one farming block directly above the player, dedicated storage boxes, natural walking with jumping and timeouts, serialized workflows with concurrent loose-pickup batches, and explicit recovery for ambiguous storage requests. No automatic tree harvesting was added because the requested first version uses manual harvesting.

User runtime evidence: v0.1.1 attaches and places a block, then times out waiting for a tile echo. Restarting places the next block and repeats the timeout. This establishes that the required echo was unavailable in that session; it does not establish which server broadcast or executor-listener behavior caused it. Version 0.1.2 verifies consumption with GetInventory and uses the normal client hit lifecycle for breaking, without an echo dependency.

User runtime evidence for v0.1.2: `prompt/image copy 2.png` shows loose drops floating above the avatar; the user reports that they remain uncollected, while another script collects without moving. Version 0.1.3 replaces walking under drops with direct UID pickup around the saved PNB grid. The native proximity condition explains a limitation of the earlier approach; server acceptance of the new requests still requires live confirmation. The requested On/Off controls derive their value from the active job and its token, including stop, completion, failure, and transfer resume.

Validation for v0.1.3: 49 offline checks passed (12 core, 35 actual generated-script runtime fixtures, two release checks), plus compilation of source, bundle, and loader using the installed Lua library. Runtime fixtures cover floating pickups, stack room, seed storage, packet reconciliation, retry readiness/cooldowns, late results after cancellation, cleanup on errors, and toggle synchronization. Services, scheduling, and server responses are mocked.

User runtime evidence for v0.1.3: `prompt/image copy 3.png` shows drops remaining in the old left and right outer columns. The user reports collection working only in the middle three columns and proceeding slowly one drop at a time. Those outer coordinates were within v0.1.3's client filter; a screenshot alone does not establish the server's reach or rejection rule. The speed cost in v0.1.3 is directly visible in its source: it awaited each `takeDrop` and then issued `GetInventory` before requesting the next UID. The supplied client's `world.ask` at `rpiyox2ca0N:3368` assigns each request a 16-bit sequence and stores independent response waiters, so different loose-drop UIDs can be requested concurrently. Version 0.1.4 launches up to eight, reserves inventory room for each item across the batch, applies accepted counts inside each request, and reconciles inventory once after all batch results settle. Gem balance is refreshed once after collection. Per-UID readiness and the one-second refusal cooldown still apply; no server-side bulk-pickup endpoint was identified.

Validation for v0.1.4: 54 offline checks passed (12 core, 40 generated-script runtime fixtures, two release checks), plus source/bundle/loader compilation. PNB recovery preserves the running job and toggle while waiting for pending requests, re-entering the saved world with `world.enter(name)`, and returning to the breaking spot. It also recognizes a picker transition observed after an invalid/interrupted action response. It does not automatically redirect from a different non-empty world name. The existing `enterWorld` implementation can return a Roblox server-teleport flag (`rpiyox2ca0N:10437`), so the farm saves a separate account-bound checkpoint and queues the loader before farming starts. Checkpoints renew during a long run, and Stop clears them. Transfer recovery retains its separate storage checkpoints.

Its own connection is disconnected on unload/reload, callbacks check the current profile setting, and repeated idle events are throttled. An unavailable executor/API call remains visible in diagnostics and does not terminate the farm. This is an engine API integration; no supplied game module is modified to implement it.

Version 0.1.7 adds the requested Discord webhook menu and an interval input in minutes. Player level uses the existing client's `GetLevel` RPC (`rpiyox2ca0N:12223`), whose first returned value is displayed as the level; gem balance uses `GetGems` (`:12254`). These two read-only requests run with a shared eight-second reporting wait and do not reconcile or mutate the backpack. Failed/timed-out values are marked unavailable. Session counters are the script's existing statistics and reset on reload. Backpack and Display Box counts read existing local data; saved boxes must be in the current world and still contain a Display Box tile. Reporting sums only the selected item's matching rows, including mixed boxes, while farming retains its dedicated-box requirement.

Discord delivery uses Delta's executor HTTP request function with a JSON POST and disabled mentions. The destination must be an HTTPS Discord webhook endpoint. Reports have their own request accounting, a 15-second HTTP wait, no overlapping unsettled requests, and HTTP 429 retry handling. Executor exceptions and response bodies are not copied to diagnostics because they can include the webhook token. Settings are validated and saved per profile with reports Off by default for older profiles. Changing reporting settings invalidates a report that has not been posted yet; disabling reports or unloading cannot recall a POST already dispatched.

The picker also has a UI lifecycle separate from the private world table. Its native `enter` callback (`lg4G5qe9g:1102`) invokes the world entry adapter, then hides the picker, invokes `hud`, and releases world-name input focus (`:1119-1121`). The direct `enterWorld` routine (`rpiyox2ca0N:10406-10520`) returns success after applying the world, without that picker cleanup. Avatar `state().active` (`:10167-10170`) checks the world name and exit-animation state, not picker visibility. Version 0.1.8 discovers this particular picker through the entry adapter identity, the `recent`/`WorldName` descendants, and its `hud` callback. Recovery checks visibility independently and performs the same HUD/focus cleanup after successful entry. A missing optional UI hook remains visible in diagnostics.

The user clarified that the requested recent server means a Recently Visited Growblox world. The picker consumes an ordered array of world-name strings from `ListWorlds` (`mG2p24qorrZ9:2866-2896`; `lg4G5qe9g:1144-1188`). Recovery selects the first entry matching the saved PNB world, or uses its saved name when the list has no match or errors. Selecting an unrelated world would invalidate the saved tile coordinates, so a different newest entry is not substituted. The selection is recorded in diagnostics. An unsettled list request prevents another entry action rather than silently abandoning ownership of that request.

Version 0.1.8 continuously reconsiders picker re-entry while waiting for loading and requires one second of stable world/avatar readiness. It rechecks state before and after inventory requests, retries malformed read-only responses up to three times, and gives a generic interrupted action a 1.5-second window to reveal an exit transition before retaining the original error. A structured picker/respawn interruption during recovery can retry, up to three consecutive interrupted recoveries. Entry denials, other-world arrivals, route failures, genuine malformed backpacks, and Stop remain terminal. These changes do not replay an ambiguous storage action as part of the inventory retry.
