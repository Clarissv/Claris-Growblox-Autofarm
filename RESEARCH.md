Design choices: named profiles, one farming block directly above the player, dedicated storage boxes, natural walking with jumping and timeouts, serialized workflows with concurrent loose-pickup batches, and explicit recovery for ambiguous storage requests. No automatic tree harvesting was added because the requested first version uses manual harvesting.

User runtime evidence: v0.1.1 attaches and places a block, then times out waiting for a tile echo. Restarting places the next block and repeats the timeout. This establishes that the required echo was unavailable in that session; it does not establish which server broadcast or executor-listener behavior caused it. Version 0.1.2 verifies consumption with GetInventory and uses the normal client hit lifecycle for breaking, without an echo dependency.

User runtime evidence for v0.1.2: `prompt/image copy 2.png` shows loose drops floating above the avatar; the user reports that they remain uncollected, while another script collects without moving. Version 0.1.3 replaces walking under drops with direct UID pickup around the saved PNB grid. The native proximity condition explains a limitation of the earlier approach; server acceptance of the new requests still requires live confirmation. The requested On/Off controls derive their value from the active job and its token, including stop, completion, failure, and transfer resume.

Validation for v0.1.3: 49 offline checks passed (12 core, 35 actual generated-script runtime fixtures, two release checks), plus compilation of source, bundle, and loader using the installed Lua library. Runtime fixtures cover floating pickups, stack room, seed storage, packet reconciliation, retry readiness/cooldowns, late results after cancellation, cleanup on errors, and toggle synchronization. Services, scheduling, and server responses are mocked.

User runtime evidence for v0.1.3: `prompt/image copy 3.png` shows drops remaining in the old left and right outer columns. The user reports collection working only in the middle three columns and proceeding slowly one drop at a time. Those outer coordinates were within v0.1.3's client filter; a screenshot alone does not establish the server's reach or rejection rule. The user chose to replace the 5 × 2 batch with one block directly above the player. Version 0.1.4 targets the nearby single-tile area, so future cycles do not generate outer-column drops. Existing outer drops require manual collection.

The speed cost in v0.1.3 is directly visible in its source: it awaited each `takeDrop` and then issued `GetInventory` before requesting the next UID. The supplied client's `world.ask` at `rpiyox2ca0N:3368` assigns each request a 16-bit sequence and stores independent response waiters, so different loose-drop UIDs can be requested concurrently. Version 0.1.4 launches up to eight, reserves inventory room for each item across the batch, applies accepted counts inside each request, and reconciles inventory once after all batch results settle. Gem balance is refreshed once after collection. Per-UID readiness and the one-second refusal cooldown still apply; no server-side bulk-pickup endpoint was identified.

Validation for v0.1.4: 54 offline checks passed (12 core, 40 generated-script runtime fixtures, two release checks), plus source/bundle/loader compilation. Added fixtures verify that three requests are in flight together with two total inventory reads (before and after), reservations prevent combined requests exceeding a stack's room, bursts stop at eight requests, cancellation retains every pending UID until settlement, returned blocks are collected before the next single-block placement, and punching waits only for the remaining initial grace period. Server acceptance, actual pickup distance, and live throughput remain unverified.

Remaining runtime questions: server rejection/correction behavior; traversability of the user's saved paths; account/world permissions; and teleport queue behavior in the installed Delta version. Offline tests do not establish those facts.
